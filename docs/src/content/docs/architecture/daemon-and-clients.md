Every piece of {{name}} is the same binary. One process, the daemon (`{{command}} serve`), owns the state; everything else is a client of it or one of its children.

## One writer

The daemon is the only process that opens the store as its writer: `internal/cli/storecmd.go` calls `sqlite.Open` for it, under the daemon's lock, and an architecture test refuses that call anywhere else outside the store's own packages. The same file holds `{{command}} store migrate` and `store restore`, which take the store's lock and stop the daemon first when it has the store open. Inside the daemon, writes go through `DB.Write`, one writer connection, and reads through a read-only pool. Every handle a process opens on one store file shares one write lock, so its write transactions queue in the process rather than polling SQLite's file lock. A command that needs the store while the daemon is down, such as the disk checks of `doctor`, opens it with `sqlite.OpenReadOnly`; `sqlite.Check` reads its schema version from the file header without opening it.

`schema.sql` is the current schema and `SchemaVersion` its version. An older store migrates forward, one version at a time, after a backup under the state directory; a release build migrates it when the daemon starts, any other build waits for `{{command}} store migrate`. A store newer than the binary is refused, and the daemon serves only its health until that changes. [Development](/architecture/development/#changing-the-stores-schema) has the steps to change the schema.

Each write notes what it changed in the daemon's change log (`internal/core/change`), kept in memory with an epoch. The read model and the clients follow it: rows are derived once from one store snapshot, revised in memory, and pulled by clients as deltas after a server-sent event.

The tasks are pulled the same way, a page since a position. A task's view also reads what is not the task's own row in the store: its units' rows, briefs and links, and its placement. The daemon has no revision per unit, so the event says which units moved: after a write of the tasks, their gates, wakes, drafts, placements, a unit's records or links, and after a row change whose units a task holds, the event carries the counters and those units, and a client that sees counters asks for the page since its position naming them (`units`). That page also holds every task holding one of them, its own unit included, those out of the view in its removed. A change too large to list is All, and it or a reconnection makes the client read its list whole.

```
a unit's row, brief or links ─┐
a task, gate, wake or draft ───┴─▶ change log ─┬─▶ read model ─▶ row change ─┐
                                               └─▶ tasks feed ◀──────────────┘
                                                       │ the units a task holds, the counters
                                                       ▼
                                           event ─▶ client ─▶ GET /api/tasks?since=…&units=…
```

An event names the rest of what moved, and a client reads only that: `plan` after a note of what `GET /api/plan` serves (a plan item's served columns, which the ledger compares before and after each write, never its save time, and its measured gain only at the tenth of a MiB or GiB a client shows, so a sweep pass that rewrites the same items notes nothing; the pending items; a session's close, whose closed sessions the plan lists; a reloaded profile), `gates` after a note of a gate or of what one shows (a draft and its items, a message, a pending plan item), `turns` after any write to a turn's book, a turn's state, a record or an answer (`GET /api/turns/live`), which can be a write the route does not show, `health` when the health a client shows moved. These flags never move the rows' position. The plan shows its units' rows, so a client also reads it again when a row change names a unit the plan holds; a reconnection reads everything again. A `notify` event carries its notices and makes no client read anything.

```
plan item, pending item, closed session, profile ─▶ plan  ─▶ GET /api/plan
gate, draft, item, message, pending item         ─▶ gates ─▶ GET /api/gates
a turn's state, record or answer written        ─▶ turns ─▶ GET /api/turns/live
a burst of health notes, the menu bar, a recheck ─▶ digest moved? ─▶ health ─▶ GET /api/health
```

The health feed builds the health after each burst of health notes (a job's end, a pause, the profile, the menu bar's status), when the menu bar connects or leaves, and every 30 seconds while a client listens, for the fields no note announces (a plugin's status, git access, the gate and effect warnings, the brief breaker's words, the viewer). It digests the health as a client shows it, without a job's last run, whether it runs, the last success of a job other than an ingestion (the sync labels read only the ingestions') and the brief queue's counts (only `doctor` reads them), and publishes only when the digest moved. A successful run of a job nobody's health shows publishes nothing; an ingestion's end moves its last success and publishes. Whether a job runs travels with no event: a client sees a sync running only when it reads the health mid-run.

The daemon computes a task's facets when it serves the task: its own facts and its brief's fields, joined with the facets of its units' rows from the read model snapshot the page already reads (see [Facets](/concepts/tasks/#facets)). Clients do no join, and the daemon counts the rail the same way: `GET /api/counters` takes the whole query as `q`, qualifiers included, and counts with the lens the clients filter with (`internal/api/lens`), so `where:general` narrows the counts as it narrows the list. `@me` in a qualifier stands for `me`. The same package places an item's facets on a row: `lens.Parts` returns, per part, the pieces each spec's `show` puts there, with their labels and the age in the profile's words, and the cockpit's lens mirrors it; `internal/api/lens/testdata/cases.json` holds the cases both run. A spec of another provider places nothing on an item, and a facet the catalog merges across providers keeps each provider's display keys in `displays`, which `FacetSpec.For` applies to that provider's rows. A task page serves each task's `reason`, its primary unit's row's. A verb that takes another task (merge, relate) picks it from `GET /api/tasks?match=<text>&except=<id>`: the open tasks but the task it picks for, whose title holds the text, case aside, whatever the view, the newest change first, each with only its id, title, state, category and units, so both clients list the same tasks however much of a view they hold. Split and unrelate pick from the task's own Merged from and Related lists, and the daemon serves them disabled, with the `nothing_to_pick` notice, while that list is empty.

The home and the decision queues read the views the same way, in one pass over the tasks (`coretasks.Service.Sets`), which the counters share: `GET /api/home` serves the briefing, the home's sections and the capture hint, `GET /api/queue` Needs you, every kind's items in the profile's order (or newest first, by `decisions.toml`'s `sort`), which the home's Needs you section, the cockpit's queue view and the menu bar read, and `GET /api/queues/{kind}` one kind's items, the oldest first, which the queue view narrowed to a kind reads, both narrowed by `q` as the counters are (see [The home and decision queues](/concepts/home/)). Every banner of what waits on the user carries one notification category, `NEEDS`, whichever kind of task, question or draft it stands for.

The reads that start while the change log's generation holds share one pass, its tasks and the facts read of each, for at most two seconds: a screen's tasks, counters, home and queues, and the tasks feed's publish before them, read every task's facts once. A write that notes a change starts a new pass, a page whose position is newer than the shared pass lists from the store, and a fact a write does not note, or one that moves with the clock, is late by two seconds at most. A pass also reads once what the facts of many tasks share: each unit's plugin facts, which `task.link_ended` and `task.placement` read, and each unit's snapshot decoded. Within one page of the queues or of a task list (`coretasks.WithPage`), what its cards read per row, a unit's turn book and a gate's message, is read once for the page; a related task, the task a gate serves and the tasks of a unit are read from the page's pass; and the GitHub facts read one view, with the events of the open tasks' pull requests loaded at once. The sweep's pass, whose GitHub `List` renews that view between reads and whose items run against the store, reads these anew each time. The sweep's pass holds only the open tasks, so a read of every task under it, a snapshot, the counters or a view, reads the store's tasks anew rather than taking the sweep's for all of them.

A page of the rows names the version of `GET /api/catalog` (`catalog`), and a page of the tasks that of `GET /api/views` (`specs`); a client holding another version reads it again, so a reloaded profile reaches it. A reload also moves every task in the next change (`all`), since it can change their facets, so a paged view reads its tasks again.

`GET /api/turns/live` serves the floating widget: the running turns, each with its intent's label, (sent or started) with their start, the turns that ended since the viewer's local midnight (newest first, at most 20, as the daemon's clock reads the day) and how many ended then in all (`done_today`), how many turns ask the user, and each intent's usual duration, the nearest-rank median (`api.QuantilesOf`, which the timings report uses too) of the turns that ended in the last 14 days, a dismissed one included. A turn of an intent whose manifest sets `reports = false` is in none of them, and a dismissed turn is not listed as done. A turn carries its task and title when a task holds its unit (an open task first), else its row's title.

## The API

`internal/api` is the one schema every client speaks: the wire types, the route paths and the version. It imports only the domain. The version is a major, sent in the `X-Loop-API` header; the daemon answers a client of another major with 426 and both versions, and a change older clients can ignore, such as a new field, keeps it.

| Role | Prefix | Who calls it | Served on |
|---|---|---|---|
| UserAPI | `/api/...` | the CLI, the terminal client, the menu bar, the cockpit | the Unix socket, and the localhost TCP port behind a token |
| AgentAPI | `/api/agent/` | the hooks and `turn end`; agent sessions through MCP | the Unix socket; MCP on its own port |
| AdminAPI | `/api/admin/` | `doctor`, `probe`, `profile try`, timings | the Unix socket only |

The TCP port answers 404 for AgentAPI and AdminAPI, refuses an unexpected `Host` and cross-site writes, and needs the token the daemon writes to its info file. AgentAPI answers while the start-up reconcile runs; UserAPI and AdminAPI wait for it.

## Transports

- **The Unix socket** carries every role, for the clients on this machine. A CLI run inside an agent session names that session on every call (`X-Loop-Session`), so the daemon applies the same authority to a shell as to the MCP tools: an agent resolves no gate, and a draft is approved by a person only.
- **Localhost HTTP** serves the cockpit's static files (`internal/web`), UserAPI and the event stream.
- **MCP** (`internal/transport/mcp`) serves the agent sessions on `127.0.0.1:47800` (`mcp.port`): `turn_end`, `task_post` and `task_read`, and the Slack tools when their plugin is enabled. A session is identified by the `X-Loop-Session` header its manager fills, never by a tool argument, and every call carries the per-install key in `X-Loop-Key`.

## Clients

A client parses input, calls one API operation and renders the answer. The daemon computes the rows, their actions, the facets, the counters and the notifications; no client derives a situation or decides which actions a row offers. An action whose answer carries a `copy` (plain text and HTML the daemon rendered from the profile) is handled the same way by every client, whatever the action: the cockpit writes the clipboard, claiming it in the click when the action's spec says `copies`, since WebKit refuses a write that starts after the answer arrives; the terminal client and the CLI copy the plain text, or print it where they cannot. Clients import only `internal/api`, `internal/api/client`, the domain and `internal/termfmt`.

- The CLI, the terminal client (`internal/client/tui`) and the menu bar (`internal/client/menubar`, its own process under its own LaunchAgent) call UserAPI over the socket.
- The cockpit calls UserAPI over HTTP. It is a Svelte 5 project in `internal/web/ui`, which Vite builds into one committed bundle, `internal/web/static/app/app.js`, embedded with the page and its stylesheet; `index.html` only loads it. Its sources under `internal/web/ui/src` each have one reason to change:
  - `state/`: the one store of what the daemon serves and of the text a reload would lose (`store.svelte.ts`), the reads that write into it (`loaders.svelte.ts`), the event stream and its debounce (`sync.svelte.ts`), the reconciliation that applies an answer in place, keeping each item a list serves again by its id (`reconcile.ts`), the route (`route.svelte.ts`), the clock ages and countdowns read (`clock.svelte.ts`), actions, overlays, the served keys and the build check;
  - `lib/`: the lens (`lens.ts`, its pieces mirroring `lens.Parts`), the catalog, the routes, the profile's strings through `t` and `tn` (`i18n.svelte.ts`), agent prose as a tree of nodes, safe by construction, only `https://` links (`markdown.ts`);
  - `components/`: the rows and boards every list draws (`rows/`), the task views, the home, the queue and the review with its Outbox step (`screens/`), the unit and task details (`detail/`, `task/`), the one decision card (`gates/`), the rail, the lens bar, Explore, the plan, the dashboard and plugin views (`chrome/`), the omnibox and overlays (`overlay/`), the keys (`keys/`) and the native window's chrome (`window/`).

  A sync writes into the store and only the nodes bound to a value that changed move: no view rebuilds DOM to reflect data, so a composer keeps its size, caret and scroll and a board its scroll across syncs ([The cockpit updates nodes; it never rebuilds them](/architecture/decisions/the-cockpit-updates-nodes-it-never-rebuilds-them/)).
- The window (`internal/client/window`) runs in the menu bar's process on macOS. It shows the cockpit's own URL in one main window, an omnibox panel, a floating widget and a window per detached task or unit, through a `Host` port that one adapter implements: `internal/client/window/wails`, the only package that imports Wails, built with the `purego` tag on darwin. The main and detached windows draw their controls over the page and mark its URL `titlebar=inset`, so the cockpit draws the title bar itself, dragged through Wails' `--wails-draggable`. It follows the event stream as the events client `window`. Any process asks it to act with `POST /api/window` (`open` a route, show the `panel`, `hide-panel`, `detach` a route's task or unit). A `{{command}}://open/#<route>` link the system hands the app reaches the window through the same `Host`, which keeps a link that launched the app until the window listens; `window.LinkRoute` reads it, for the app and for `{{command}} open`. The daemon relays the request only to that client, without moving the rows' position, and answers whether one took it, so `{{command}} open` falls back to the browser when none did. The panel's page reaches the window the same way, through the panel's routes (`components/window/panel.ts`), with no bridge between Go and the page.
- The floating widget is two windows: the tab, which carries the counts, and the panel window beside it, which shows the queue or a peek. Each is a borderless, transparent, non-activating panel at the floating level that joins every space, stays put in Mission Control and is left out of the window cycle; each shows over a full-screen app only when `window.float_over_full_screen` allows it. Wails sets the level of a window created hidden from its `AlwaysOnTop` option as the window first becomes key, so the float's windows and the omnibox panel all set it, and stay at the floating level after a click. The widget exists only while `menubar.Config.Float` is on; `window.float` turns it on, and it is off by default. The tab loads the cockpit's `#/float/tab` route when the float shows; the host makes the panel window, hidden, on the first open or peek, loads `#/float/panel` in it, and keeps it afterwards, loading it anew only at a new daemon address or when its page never reported in. They are the windows whose pages talk to Go directly. Through the message handler Wails injects (`webkit.messageHandlers.external.postMessage`) each page sends one JSON object per message, named in `type`, and the host names the window it came from (`window.FloatMessage.Window`); the host drops such a message from any other window, from a child frame or from an origin other than the one that window loaded. The message set, and the bridge calls back on each page's global named after the command (`window.FloatBridge`, `<command>Float`), are:

  | From | Message | What the host does |
  |---|---|---|
  | tab | `{"type":"float:size","w","h"}` | sizes the tab around its anchor corner; a size it already has moves nothing |
  | tab | `{"type":"float:panel"}`, with `"toggle":true` on a click | opens the panel window beside the tab, or closes it on a toggle while the full panel shows |
  | tab | `{"type":"float:peek","item"}` | asks the panel's page to peek at the item of that key, unless the full panel shows or the tab is being dragged |
  | panel | `{"type":"float:size","w","h","mode"}` | places and shows the panel window at that size beside the tab, and keeps `mode` (`peek` or `panel`) as what it shows, so a peek the page turned into the panel closes on a toggle; the window shows only at a size the page sent for what it was last asked to show |
  | panel | `{"type":"float:close"}` | hides the panel window and tells the page it is closed, so a show it took meanwhile does not leave it drawing in a hidden window; the page sends it once as it loads, which tells the host it can be told what to show |
  | either | `{"type":"float:open","route"}`, `{"type":"float:hide","mode"}` | shows the route in the main window; runs the hide hook |

  | To | Bridge call | When |
  |---|---|---|
  | tab | `place({edge})` | once its page has loaded, after a drop and when the screens change; it also ends a drag whose release the page missed |
  | panel | `show(mode, {item, side, maxW, maxH})` | to show `panel` (on `item`, else on the item last peeked at), `peek` at `item`, or `""` to close; `side` is the side of the tab the window sits on and `maxW`, `maxH` the room there (`window.PanelRoom`), which bounds what the page draws, since the window's viewport is only as large as what the page draws |
  | panel | `leave()` | the pointer has been off both windows for `floatGrace` (150 ms) while the full panel shows, counted from the pointer last leaving a window or from the full panel showing, whichever is later (a move over a window counts as being over it, since a window shown under a still pointer gets no entry); the page closes unless pinned |
  | panel | `blur()` | the panel window resigned key while the full panel shows, which WebKit may not tell a non-activating panel's page; the page closes unless pinned |

  The tab never becomes key: AppKit asks the host, which always says no, so a click or a drag on it never takes the keyboard from the app the person types in. The panel window becomes key only while the controller last showed it as the full panel (`Host.ShowFloatPanel` takes the mode, which the controller passes only at a size the page drew for what it was last asked), so a late size of the page never makes a hidden window keyable; hiding it hands the keyboard back. The panel window goes on the side of the tab `window.PanelRoom` picks from the tab alone (away from a docked edge, or below or above a free tab, whichever has more room), against the tab, lined up with the tab's side nearer the screen's middle and inside the visible frame of the tab's screen (`window.PanelFrame`), so it never covers the tab, and the tab never moves for it. Neither window paints outside what its page draws: each web view draws no background of its own (`drawsBackground` off), since in a transparent panel WebKit would otherwise fill the window with the color scheme's background. Neither window catches the mouse outside what its page draws, and neither needs to be key for it: each web view accepts the first click, and since WebKit drops the mouse's moves in a window that is not key, a tracking area active in any window turns the pointer entering, moving over and leaving each window into the page's pointer and mouse events at that point (they are synthetic, so CSS `:hover` does not follow them: the page marks what the pointer is over with `data-hover` from `pointerenter` and `pointerleave`, styled beside `:hover`); the same tracking tells the host the pointer entered or left each window, which is what the leave grace follows: leaving one window starts it, entering either cancels it, so crossing from the tab to the panel, or back, never closes the panel. Every Wails window and web view is observed through key-value observing, so the host cannot swap a subclass onto the float's instances alone; it replaces `canBecomeKeyWindow` and `acceptsFirstMouse:` on their classes with methods that answer for each float window and call the earlier method for every other instance, which leaves the omnibox panel and the other web views as they were. The tab's page drags its window with Wails' native drag (`wails:drag`), and ends a drag on the pointer's release, on the host's next `place`, or on the next drag, since the window server may keep the release from the page; the host follows the drag from the first move to the release of the mouse button, polling every 30 ms in goroutines its worker starts and its stop awaits (as quitting stops the host it waits for them at most 2 seconds, since work that waits on the main thread never returns once the app's loop has ended), closes the panel as the drag starts, holds any `float:size` until the drop, then the controller keeps the drop's placement (`window.FloatPlacement`: docked on the left or right edge it was dropped near, or free, and its anchor point, the corner of its screen's quarter) in the app's user defaults under `window.PlacementKey`, in the brand's domain, and snaps the frame to its edge. A frame belongs to the screen whose frame holds most of it, or to the main screen when none holds any, as when its screen was unplugged; `window.ClampToScreens` keeps the tab inside that screen's visible frame (without the menu bar and the Dock), again whenever the screens change, and a shown panel is placed anew beside it. The tab's page detects arrivals and keeps the one-peek-per-burst rule; the panel's page shows the peek for its while, lets its card fade out, then sends `float:close`. `float:hide` runs the hook that `window.Controller.OnFloatHide` sets, and the `window.float_hotkey` chord runs the one `OnFloatHotkey` sets; the app points both hooks at the menu bar.
- The menu bar decides what the float shows (`menubar.Visibility`: shown, quiet, snoozed until a time, or off) and calls the window controller's `ShowFloat` and `HideFloat`. The visibility is saved beside the placement, under `menubar.VisibilityKey`, and loads once (`Controller.StartFloat`): before the daemon answers when it is down at launch, else as `Run` starts. Until it loads, nothing moves the float. An arrival is a key of `GET /api/queue`'s items absent from the last read; an item's key is its gate, else its task, its kind and its situation's provider, kind and unit, as the float's page keys it. A read that fails changes nothing, so a daemon restart is no arrival. The first read after launch only learns the queue, except in quiet: while quiet, each read saves the queue's keys with the visibility, and the first read after a relaunch compares against them, so what arrived while the app was closed brings the float back. A snooze ends on a timer. A sleeping Mac stops that timer, so while snoozed the menu bar also compares the wall clock with the snooze's end once a minute (`snoozeTick`), and on any successful refresh; a snooze that slept past its end shows the float within a minute of waking. The timer, the redraws that follow a move and the daily digest's loop run in goroutines the menu bar starts only while `Run` runs; as `Run` ends it stops every move under the float's lock, then waits on them. While the float is quiet or snoozed, or shown with a tab whose page has reported in (`window.Controller.FloatReady`, which `menubar.Config.FloatReady` reads; only the tab counts, since the panel's page loads only as the panel first opens) or that it asked to show less than `floatLoadGrace` (4 s) ago, the menu bar posts no `NEEDS` banner; a goroutine the menu bar starts while `Run` runs, and waits on as it ends, redraws as the grace ends, so the banners post when the page never reported in; the window controller's `OnFloatReady` hook redraws the menu bar as the tab's page first reports in after a load, which withdraws the banners the float now carries.
- The daemon serves the float's pages, so a `ShowFloat` the daemon cannot serve (no `http.json`) leaves the float wanted and returns its error; the window controller shows a wanted float again each time its events stream subscribes after a lost one, and on any subscription while its page has not reported in. `Host.ShowFloat` takes whether to load the tab's page anew: the controller reloads it when its URL changed or its page has not reported in since its last load (a page the daemon refused never does), and keeps a loaded page at the same URL, which learns its place at once. A panel page that never reported in loads anew on the next open after the events stream subscribes again.
- The hooks (`internal/client/hook`) call AgentAPI with a 2-second budget, allow on any failure and never block an agent except to hold a stop that owes a record.

With the daemon down, every client fails within a second and names the fix, and nothing is spooled for later. Only the local checks of `doctor` and the developer tools read the store then, read-only.

## Children

The daemon starts the headless agent calls (the brief, headless turns, the Slack extraction, profile dry runs) as its own children through the agent's port. They are no clients and never reach the store. Each `claude -p` the daemon runs leads its own process group. A cancelled call sends the group SIGTERM, then SIGKILL after five seconds; once the call ends, whatever it left in the group is stopped the same way, and a stopping daemon kills every group still running. The daemon lists the live groups in its state directory, so after a crash the next start kills what the crashed one left. Every package that spawns a process imports `internal/meter`, so `{{command}} doctor --load` counts each spawn.

## Authority

Agents report facts; only your surfaces grant authority: endorsing a verdict, approving a draft, taking over a pull request, removing a workspace. Every post the loop makes is a draft first, and only an approved draft reaches the plugin's publisher. Every write an agent makes in your name goes through `github_post` or `slack_post` as a draft; with `draft: false` from a session you drive, the session approves it at once. Rounds can still publish on GitHub through `gh`. The loop never hands an agent a source's token; agents read and draft Slack through the daemon's tools. [Security](/concepts/security/) states the limits of this boundary.
